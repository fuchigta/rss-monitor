# ADR 001: システムアーキテクチャとコンポーネント選定

## ステータス

Accepted

## 日付

2025-10-27

## コンテキスト

RSSフィードの更新頻度とはてなブックマーク数を定点観測し、しきい値を下回った際にアラートを発生させるモニタリングシステムを構築する必要があった。

要件：
- RSSフィードの定期的な収集と監視
- はてなブックマーク数の取得と追跡
- メトリクスの時系列データ保存
- しきい値ベースのアラート機能
- データの可視化とダッシュボード
- 簡単にセットアップできる構成
- 評価項目（メトリクス）の拡張性
- なるべくOSSの組み合わせで実装範囲を最小化

## 決定内容

以下のコンポーネント構成を採用する：

### コアコンポーネント

1. **PostgreSQL 16** - データベース
   - RSSフィード情報、エントリ、メトリクス、アラートの永続化
   - JSONB型による柔軟なメタデータ保存
   - 時系列データに対する効率的なクエリ

2. **Python 3.11** - アプリケーション層
   - RSSフィード収集（feedparser）
   - はてなブックマークAPI統合（requests）
   - メトリクス評価ロジック
   - アラート判定

3. **Grafana** - 監視・可視化
   - PostgreSQLデータソース統合
   - ダッシュボードによるメトリクス可視化
   - アラート履歴の表示

4. **Ofelia** - ジョブスケジューラ
   - 定期的なデータ収集とメトリクス評価
   - Docker環境に最適化されたcronライクなスケジューラ
   - 設定ファイルベースの簡単な管理

## 結果

### 良い影響

1. **最小限の自前実装**
   - 既存のOSSを活用することで開発工数を削減
   - 各コンポーネントは成熟したツールで信頼性が高い

2. **シンプルな構成**
   - 各コンポーネントの責任範囲が明確
   - トラブルシューティングが容易

3. **拡張性**
   - PostgreSQLのスキーマ拡張が容易
   - Pythonアプリケーションへの機能追加が簡単
   - Grafanaダッシュボードのカスタマイズが柔軟

4. **運用性**
   - Docker Composeによる統合管理
   - 各コンポーネントの独立性により個別のスケーリングが可能
   - 既存のモニタリング・ログ収集ツールとの統合が容易

### 懸念事項とトレードオフ

1. **コンポーネント数**
   - 4つのコンポーネント管理が必要
   - しかしDocker Composeで一元管理することで緩和

2. **リソース消費**
   - 各コンポーネントが独立したコンテナとして動作
   - 小規模利用でもある程度のリソースが必要
   - ただし要件を満たすには許容範囲

3. **学習コスト**
   - 各ツールの知識が必要
   - しかし全て広く使われているOSSで情報が豊富

## 代替案

### 案1: オールインワンAPMツール（Prometheus + Alertmanager）

**検討理由**: 監視に特化した統合ソリューション

**却下理由**:
- RSSフィード収集機能がない（自前実装が必要）
- はてなブックマークAPIとの統合が複雑
- 要件に対してオーバースペック

### 案2: サーバーレス構成（AWS Lambda + DynamoDB + CloudWatch）

**検討理由**: インフラ管理不要、スケーラブル

**却下理由**:
- ローカル環境での動作が要件
- ベンダーロックインのリスク
- 小規模利用ではコストが高い可能性

### 案3: モノリシックPythonアプリ（Flask + SQLite + APScheduler）

**検討理由**: シンプル、単一アプリケーション

**却下理由**:
- ダッシュボード機能を自前実装する必要がある
- SQLiteは並行アクセスに弱い
- スケーラビリティに課題

### 案4: Elasticsearch + Kibana + Logstash (ELKスタック)

**検討理由**: 強力なログ分析・可視化機能

**却下理由**:
- リソース消費が大きい
- 要件に対してオーバースペック
- セットアップと運用が複雑
